# Структура репозитория и порядок реализации

## Структура

Показан верхний уровень. Внутреннее устройство модулей — на усмотрение исполнителя.

```
avi-hack/
├─ README.md                 вход в проект; после реализации — раздел «Как запустить»
├─ docs/                     план, ТЗ, реестр экспериментов (этот каталог)
├─ task/                     материалы организаторов (не менять)
├─ dataset/public/           исходные данные (не менять)
├─ prompts/                  подсказки для моделей-исполнителей кода
├─ configs/default.yaml      все настраиваемые значения: пороги, веса, пути, адрес LLM, режим
├─ data/
│  ├─ challenge/             трудные примеры, написанные вручную (в git)
│  └─ processed/             производные таблицы (не в git, воспроизводятся командой)
├─ src/avito_drafts/         код решения одним пакетом:
│                            нормализация и данные · оценка · слои классификации ·
│                            клиент LLM и тексты подсказок · черновики (фрагменты,
│                            генерация, проверки, шаблон) · единая функция предсказания
├─ scripts/                  по одному запускаемому сценарию на шаг: подготовка данных,
│                            обучение, оценка, пакетное предсказание, замеры
├─ app/                      демо на Gradio
├─ tests/                    несколько проверок: метрика, формат ответа, нормализация
├─ artifacts/                обученные модели: tfidf/ (в git), encoder/ (не в git)
├─ models/                   скачанные веса (не в git)
├─ reports/                  runs.jsonl, benchmark.json, submissions/, рисунки для слайдов
└─ scratch/                  разведочные скрипты (не в git)
```

Правила:

- Тексты подсказок для LLM лежат отдельными файлами, а не строками в коде: их правят чаще всего.
- Ни одного числа-параметра в коде: всё в `configs/default.yaml`.
- Веса LLM и энкодера в репозиторий не попадают (требование организаторов); в README — команды из [09_downloads.md](09_downloads.md).
- В окружении `transformers` версии 5.x: интерфейсы сверять с установленной версией, а не по памяти.

## Порядок реализации

Часы — от начала реализации; это бюджет, а не обещание. Главный принцип: после шага 1 в любой момент есть работающее решение, каждый следующий шаг только добавляет.

| Шаг | Часы | Что делается | ТЗ | Готово, когда |
| --- | --- | --- | --- | --- |
| 0 | 0:00–0:30 | Проверка окружения: пакеты, GPU, ответ Ollama по JSON-схеме на одном запросе, загрузка BERTA, распределение длин текстов в токенах | [09](09_downloads.md) | Все проверки напечатали «ОК»; длины в токенах записаны в ТЗ 2 |
| 1 | 0:30–2:00 | Данные, инструмент оценки, правило по ключевым словам, слой 1, единая функция в режиме `classify`, пакетный запуск | [01](01_spec_data_eval.md), [02](02_spec_classification.md) слой 1, [04](04_spec_service_demo.md) | **Контрольная точка А**: файл в → JSONL в формате организаторов; D1 и C1 в реестре |
| 2 | 2:00–4:30 | Клиент LLM, отбор фрагментов, генерация черновиков, шаблонный черновик | [03](03_spec_drafts.md) шаги 1, 2 и шаблон | Пример из постановки даёт осмысленный черновик; G1 в реестре |
| 3 | 4:30–6:00 | Демо (обе вкладки) и режимы `fast` / `full` | [04](04_spec_service_demo.md) | **Контрольная точка Б**: полный сценарий показывается в браузере |
| 4 | 6:00–8:30 | Дообучение энкодера, смесь со слоем 1, пороги | [02](02_spec_classification.md) слои 2 и 4 | C2, C3, C6, C12 в реестре |
| 5 | 8:30–10:30 | Признаки оговорок, LLM-проверяющий, каскад | [02](02_spec_classification.md) слои 3 и 5 | C4, C5, C7, C13 в реестре |
| 6 | 10:30–12:00 | Проверки черновиков, перегенерация, ручная оценка 30 пар | [03](03_spec_drafts.md) шаги 3–4 | G2, G3 в реестре; таблица для просмотра создана |
| 7 | 12:00–13:00 | Замеры скорости и памяти | [04](04_spec_service_demo.md) | `reports/benchmark.json`; S1, S2 в реестре |
| 8 | 13:00–14:30 | **Возврат к автору плана**: разбор реестра, выбор итоговой конфигурации и кандидатов на попытки отправки | [06](06_experiments.md) | Итоговые значения в `configs/default.yaml`; решения записаны в реестр |
| 9 | по расписанию организаторов | Приватный набор: прогон, проверки без эталона, отправки | [02](02_spec_classification.md), раздел о попытках | Таблица попыток в реестре заполнена |
| 10 | оставшееся время, не меньше 3 часов | Презентация, раздел «Как запустить», репетиция демо на чистом запуске, запас | [05](05_presentation_plan.md) | Демо проходит репетицию дважды подряд |

Если исполнителей двое, шаги 2–3 и 4–5 идут параллельно: первый делает черновики и демо, второй — классификацию. Общая часть — клиент LLM; его делает первый, второй подключает на шаге 5.

Что бросать первым, если времени не хватает (в этом порядке): эксперименты приоритета 3; слой 3 как отдельные признаки (оставить только жёсткое правило оговорок, если C7 его подтвердил); альтернативные энкодеры; перегенерация (оставить проверки и шаблон). Не бросать: контрольные точки А и Б, замеры, реестр.

## Как ставить задачу исполнителю

Одна задача — один шаг таблицы. В задаче указать: прочитать `README.md`, этот файл и ТЗ шага; реализовать; выполнить критерии приёмки из ТЗ; записать результаты в `reports/runs.jsonl` и в реестр; значения из разделов «Требует проверки» не подбирать молча, а записывать замер рядом. Отклонения от ТЗ записывать в конец соответствующего ТЗ в раздел «Отклонения при реализации» с причиной.
